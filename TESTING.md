# Как мы тестируем

Одна команда для всех проверок перед коммитом:

```sh
make check
```

Она прогоняет четыре уровня:

| Уровень | Команда | Что проверяет |
| --- | --- | --- |
| Типы | `cd frontend && npx tsc --noEmit` | TypeScript-контракты фронтенда |
| Стили | `cd frontend && npm run lint` | ESLint: React-хуки, импорты, мусор |
| Бэкенд | `docker run … golang:1.27.1-alpine go test ./...` | Go-тесты бэкенда в изолированном контейнере |
| E2E | `node --test e2e/` | Весь путь заявки через HTTP, как в браузере |

## E2E: философия

Тесты — это сценарии реального API: логин, создание заявки, действия сотрудника,
подпись. Ходят по HTTP через next-прокси (`/api/*`, `/esign/*`), то есть проверяют
ещё и проксирующие rewrite'ы фронтенда. Написаны на встроенном `node:test`,
зависимостей не имеют.

Запуск по отдельности:

```sh
node --test e2e/                       # все 8 (нужны стек и frontend на :3000)
node --test --test-name-pattern="Старт" e2e/pipeline.test.mjs
make e2e                               # с проверкой доступности frontend
E2E_BASE=http://localhost:8080 make e2e  # напрямую в backend (esign возьмётся с :8084)
```

## Карта тестов (8 тестов)

| Файл | Тест | Что покрывает |
| --- | --- | --- |
| `accounts.test.mjs` | `demo.ip.overdue` | Автоотказ пайплайна без сотрудника, отсутствие предложения и действий |
| `accounts.test.mjs` | `demo.ooo.good` | Контрпредложение по экспресс-кредиту клиенту и отказ от него кнопкой (→ cancelled) |
| `accounts.test.mjs` | `demo.ooo.no-data` | **ООО без фин-данных**: источник не дал данных → CSV → submit |
| `accounts.test.mjs` | `demo.ip.no-data` | **ИП без фин-данных**: тот же резервный путь с CSV |
| `concurrent.test.mjs` | длинный сценарий | Клиент и сотрудник одновременно: поллины, take, запрос уточнений, 409 и повтор, approve, подпись, выдача (issued), PDF с обеих сторон |
| `pipeline.test.mjs` | `demo.ooo.good` | «Старт»: залог + денежный план → оба заключения → пересчёт скоринга → одобрение → подпись → issued |
| `pipeline.test.mjs` | `demo.ooo.good` | Овердрафт целиком: одобрение с условиями лимита → подпись → открытие лимита (issued) |
| `pipeline.test.mjs` | `demo.ooo.no-history` | retry-checks → retry-scoring → ручной отказ с причинами |

Все действия сотрудника покрыты: `take`, `request-info`, `collateral-review`,
`cash-plan-review`, `retry-checks`, `retry-scoring`, `decision`
(approved / counter_offer / rejected).

## Подводные камни (правила бэкенда, которые отражены в тестах)

- **Каждое тело мутации** содержит `expected_revision`, создание/отправка/подпись/отказ — ещё и
  `Idempotency-Key` (иначе 400 «Передайте заголовок Idempotency-Key»).
- **collateral-review и cash-plan-review возвращают не карточку** — после вызова
  перечитывайте `staffCard` (в UI это делает `onActed`).
- **CSV**: суммы в рублях с двумя знаками после точки (`8500000.00`); только завершёншиеся месяцы; месяц не раньше
  регистрации компании; ИНН в строках = ИНН компании. Помощник `lastCompletedMonth()`.
- **«Старт»**: стоимость проекта = кредит + собственные; собственные ≥ 30% стоимости;
  до `sales_start_month` в прогнозе доход нулевой; прогноз ровно на срок кредита;
  стресс-модель (0.9·доход, остаток ≥ 0, хвост 6 месяцев покрывает платёж) —
  поэтому в тесте доходы после старта продаж завышены с запасом.
- **Залог**: сумма заявки ≤ 70% принятой стоимости залога, иначе
  `COLLATERAL_INSUFFICIENT`.
- **Положительное решение требует `CanPublish` у скоринга** (политика FSM): завершённый
  скоринг, покрытие C ≥ 1.2·(долг+платёж), стресс ≥ долг+платёж, score ≥ 600. Демо-данные
  покрывают только `demo.ooo.good`, и максимум — экспресс ~100 000 ₽ на 24 месяца
  (стресс-поток ≈ 11 000 ₽/мес). Поэтому все positive-тесты построены на `express 100k/24`
  этой компании; сценарии `thin` имеют окно данных 2025 года — вне окна модели.
- **После заключений нужен пересчёт скоринга**: collateral-review/cash-plan-review меняют
  данные, но не пересчитывают модель — в тесте вызывается `retry-scoring`, и решение ждёт
  пустых `decision_blockers`.
- **Овердрафт**: сборка scoring-input заполняет поля, которых нет в API
  (`fillOverdraftDefaults` в `scoring/database.go`): дата поступления — конец траншевого
  окна, сумма — лимит с процентами, основание — цель кредита, версия каталога — код
  продукта, снимки — из `financial_snapshots`; подтверждения TERMS/INFLOW фиксируются по
  текущим данным. Транш в тесте — 60 дней (максимум): ёмкость модели должна покрывать
  лимит. Окно финансов `demo.ooo.good` умножено ×6 в `financials-mock/testdata` —
  обороты позволяют лимит 100 000 ₽ при min-сумме продукта.
- **Выдача асинхронна**: после подписи issue-worker (интервал 500 мс) переводит
  `signing → issued` — тесты ждут статус через `waitForIssued`.
- **Отказ клиента**: `POST /applications/{id}/decline` тоже требует
  `Idempotency-Key`; доступен только из `approved`/`counter_offer` → `cancelled`.
- Пайплайн асинхронный: после submit/retry ждём статусы и ревизии через `until`
  (поллинг с таймаутом), а не фиксированные sleep.

## Необратимость и чистка

Тесты создают реальные заявки, решения и подписи в демо-БД. Чистое состояние:

```sh
make db-reset CONFIRM=1
```

## Что не покрыто автоматикой

- Браузерный UI: мастер кликом, тур, подпись в диалоге — вручную по сценарию из
  README (два окна: клиент и банкир), проверка страниц `curl`-дымом (`/`, `/login`,
  `/cabinet`, `/guide`, `/underwriter`).
- Мобильная вёрстка — вручную.

## Как добавить тест

1. В `e2e/helpers.mjs` уже есть входы, поллинги (`until`), `startApplication`
   (с опциями `request`/`extras`), действия сотрудника (`staffPost`) и подпись
   (`signLoan`). Новое — сюда.
2. Называйте тест по аккаунту и сути: `demo.ooo.thin: …` — по описанию видно, что
   проверяется.
3. Прогоните файл точечно (`node --test --test-name-pattern=… e2e/…`), затем
   полный `make check`.
