# Lasagna API: Postman

Необходимо для импорта в Postman

## Импорт

1. Импортируйте `Lasagna.postman_collection.json` и `Lasagna.postman_environment.json` в Postman.
2. Выберите environment **Lasagna local**.
3. Укажите учётные данные в `client_email`, `client_password`, `underwriter_email` и `underwriter_password`.
4. `base_url` по умолчанию — `http://localhost:8080`.

Пароли и токены в экспортированных файлах пусты. После успешного `POST /auth/login` тест скрипт сохраняет `access_token` в соответствующую переменную окружения. Защищённые запросы используют `client_token` или `underwriter_token`; копировать токены вручную не нужно.

## Запуск backend и демо-данных

Нужен Docker Compose. Из каталога `lasagna`:

```powershell
Copy-Item .env.example .env.docker
docker compose up -d --build
docker compose wait demo-seed
docker compose logs demo-seed
```

Копирование `.env.example` требуется только при первом запуске и только если `.env.docker` ещё не создан. Дождитесь успешного завершения `demo-seed` (`demo seed completed accounts=12`). Локальный backend доступен на `http://localhost:8080`; полный стек также запускает frontend на `http://localhost:3000`.

Для локальных демо-данных можно использовать:

| Переменная | Значение |
| --- | --- |
| `client_email` | `demo.ooo.good@lasagna.test` |
| `client_password` | `DemoCabinet2026!` |
| `underwriter_email` | `underwriter@lasagna.demo` |
| `underwriter_password` | `DemoUnderwriter2026!` |

Можно выбрать другой демо-email клиента из [`docs/demo-businesses.md`](../demo-businesses.md). ID компании на новой базе будут отличаться: запрос `GET /companies` автоматически сохраняет `id` первой компании в `company_id`.

## Основной сценарий кредитования

Запустите папку **Основной сценарий кредитования** через Postman Runner и выполняйте запросы по порядку. Используются демо-компания клиента, кредитный продукт и образцы полей из Swagger.

1. Войти как клиент; `client_token` сохранится автоматически.
2. Получить компании и кредитные продукты.
3. Создать заявку; ответ сохранит `application_id` и `application_revision`.
4. Заполнить заявку. Пример настроен на `working_capital`; поля можно изменить в соответствии с реальной потребностью и Swagger.
5. Получить финансовые данные и проверить их состояние.
6. Отправить заявку и проверять её статус повторным запуском `GET /applications/{id}`. Обработка асинхронная, поэтому может потребоваться ожидание. Не переходите к сотруднику банка, пока заявка не появится в очереди проверки.
7. Войти как сотрудник банка; затем получить очередь и карточку заявки, взять её в работу и отправить решение. Ответы с `revision` обновляют `application_revision`.
8. Как клиент, получить предложение и договор. Их идентификаторы сохраняются для запроса контекста подписи.
9. Подписание требует криптографической подписи, которую коллекция не генерирует. Используйте подписывающий frontend и локальный ESign mock вручную (демо PIN: `12345678`); после успешного подписания пропустите `POST /applications/{id}/sign` в Runner и выполните `GET /applications/{id}/signature`. Если вызываете `POST /applications/{id}/sign` из Postman, сначала вручную получите подпись и заполните переменную `signature`. Секрет PIN не передаётся backend.

Результат решения зависит от данных заявки и бизнес-проверок: пример решения не обходит проверки и не гарантирует одобрение. Если финансовый источник не вернул данные, приложите CSV в поле `file` запроса `POST /applications/{id}/financials/csv` либо используйте подтверждение отсутствия истории только для продукта «Старт». Не отправляйте заявку, пока финансовый шаг не завершён.

Для подключения новой компании вместо демо-компании нужны запросы `POST /companies/challenges` и `POST /companies`; оба шага зависят от подписи через ESign mock и требуют ручного взаимодействия.

### Повторный запуск и Idempotency-Key

Для всех операций, где Swagger требует `Idempotency-Key`, pre-request script создаёт UUID и сохраняет его в переменной окружения. При повторе запроса ключ остаётся тем же, чтобы сервер мог распознать повтор операции. Чтобы создать новую операцию (например, ещё одну заявку), очистите переменную `idempotency_key_post_applications` перед запуском соответствующего запроса.

## Папки endpoints

Папки **Applications**, **Financials**, **Auth**, **Companies**, **Credit Products**, **Documents**, **Underwriting** и **Users** покрывают операции из Swagger. У запросов настроены метод, маршрут, параметры, заголовки, примеры тел и простые проверки статуса/ключевых полей. Запросы загрузки CSV требуют вручную выбрать файл в поле `file`.

## Ограничения спецификации

- Swagger задаёт BearerAuth для защищённых методов, но не документирует требуемую роль пользователя для каждого endpoint. Для маршрутов `/users` коллекция использует токен сотрудника; если локальная конфигурация требует другую роль, её нужно уточнить отдельно.
- Swagger не описывает полный криптографический обмен с ESign mock. Поэтому получение подписи и подписание не автоматизированы скриптами Postman.
- Обработка заявки асинхронна, а значения решения могут быть отклонены бизнес-валидацией. Проверяйте фактический ответ и статус; коллекция не подменяет результаты обработки.
