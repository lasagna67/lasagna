# Registry Mock

Отдельный HTTP-сервис на Go 1.22+ и стандартной библиотеке, имитирующий ЕГРИП и ЕГРЮЛ. Загружает два JSON-массива при запуске и ищет отчёты по ИНН в отдельных индексах в памяти.

## Запуск

Команды выполняются из `lasagna/registry-mock`:

```powershell
go run .
```

По умолчанию данные ИП находятся в `testdata/egrip.json`, данные юридических лиц — в `testdata/egrul.json`, порт — `8081`. Оба файла содержат JSON-массивы объектов `inn/status/report`. Сервис только читает эти файлы. Относительные пути разрешаются от текущего рабочего каталога.

Пути можно настроить независимо:

```powershell
$env:EGRIP_DATA_PATH = './testdata/egrip.json'
$env:EGRUL_DATA_PATH = './testdata/egrul.json'
go run .
```

Настройки:

| Переменная | По умолчанию | Назначение |
| --- | --- | --- |
| `EGRIP_DATA_PATH` | `testdata/egrip.json` | Путь к JSON-массиву отчётов ЕГРИП |
| `EGRUL_DATA_PATH` | `testdata/egrul.json` | Путь к JSON-массиву отчётов ЕГРЮЛ |
| `PORT` | `8081` | Порт HTTP-сервера |

Если любой файл недоступен, JSON повреждён, вход не является массивом или ИНН повторяется внутри файла либо между файлами, приложение завершается с ошибкой загрузки до запуска HTTP-сервера. После изменения данных сервис нужно перезапустить. Прежние `companies.json` и `REGISTRY_DATA_PATH` заменены двумя отдельными источниками.

## Docker

Сборка и запуск из `lasagna/registry-mock`:

```powershell
docker build -t registry-mock .
docker run --rm -p 8081:8081 registry-mock
```

Dockerfile собирает статический Go-бинарник, затем копирует его и существующие `testdata/egrip.json` и `testdata/egrul.json` в образ Alpine Linux. Приложение запускается от пользователя `app`, порт — `8081`. Оба JSON-файла должны существовать до сборки; изменения данных попадают в образ при повторной сборке.

Чтобы использовать локальные JSON без пересборки образа, подключите каталог с обоими файлами только для чтения:

```powershell
docker run --rm -p 8081:8081 --mount "type=bind,source=$((Resolve-Path './testdata').Path),target=/app/testdata,readonly" registry-mock
```

Переменные `PORT`, `EGRIP_DATA_PATH` и `EGRUL_DATA_PATH` можно переопределить через `docker run -e`. При смене `PORT` также измените проброс порта `-p`.

## API

```powershell
curl.exe http://localhost:8081/health
curl.exe http://localhost:8081/v1/egrip/770761836401
curl.exe http://localhost:8081/v1/egrul/7705005410
```

`GET /health` возвращает `200` и `{"status":"ok"}`.

`GET /v1/egrip/{inn}` ищет ИП в ЕГРИП и принимает ИНН из 12 цифр. `GET /v1/egrul/{inn}` ищет юридическое лицо в ЕГРЮЛ и принимает ИНН из 10 цифр. Общий маршрут `/v1/companies/{inn}` удалён и возвращает `404 NOT_FOUND`.

Успешный ответ имеет формат:

```json
{
  "inn": "7705005410",
  "status": "ok",
  "report": {
    "business_type": "ООО",
    "name": "ООО «Кедровый контур Демо»",
    "registration_date": "2012-04-17",
    "business_status": "active",
    "okved": [
      {"code": "25.62", "name": "Обработка металлических изделий механическая"},
      {"code": "25.61", "name": "Обработка металлов и нанесение покрытий на металлы"},
      {"code": "46.72", "name": "Торговля оптовая металлами и металлическими рудами"}
    ]
  }
}
```

В `business_type` указано `ИП` или `ООО`. `status: "ok"` означает успешное получение отчёта и не зависит от состояния бизнеса. У прекративших деятельность записей `business_status: "terminated"` и присутствует `termination_date`; у действующих записей этого поля нет. При миграции `ceased` и `liquidated` приведены к `terminated`, дата прекращения перенесена из прежнего `status.since`. Сценарии реорганизации сохранены с `business_status: "reorganizing"`.

Все 20 прежних ИНН, названия, даты регистрации и коды ОКВЭД сохранены: 10 отчётов в каждом файле. Основной ОКВЭД идёт первым, затем дополнительные. Названия ОКВЭД сверены по [классификатору ОКВЭД2](https://classinform.ru/okved2/); например, [25.62](https://classinform.ru/okved2/kod-25.62.html). Поля старой модели, включая `source`, `entity_type` и `metadata`, в новом контракте отсутствуют.

| Статус | Код ошибки | Условие |
| --- | --- | --- |
| `200` | — | Компания найдена |
| `400` | `INVALID_INN` | ИНН не состоит из 12 ASCII-цифр для ЕГРИП или 10 для ЕГРЮЛ |
| `404` | `COMPANY_NOT_FOUND` | ИНН отсутствует в реестре |
| `500` | `INTERNAL_ERROR` | Внутренняя ошибка; детали остаются в серверном журнале |
| `405` | `METHOD_NOT_ALLOWED` | Для эндпоинта использован метод, отличный от GET |
| `404` | `NOT_FOUND` | Неизвестный маршрут |

Формат ошибки:

```json
{"error":{"code":"COMPANY_NOT_FOUND","message":"Company not found"}}
```

Контрольные цифры ИНН на первом этапе не проверяются.

## Устройство

- `main.go`: конфигурация, сборка зависимостей и HTTP-сервер с таймаутами.
- `internal/handler`: отдельные маршруты ЕГРИП/ЕГРЮЛ, HTTP-статусы и JSON-ответы.
- `internal/service`: проверка ИНН и вызов интерфейса `Repository`, объявленного в этом пакете.
- `internal/repository`: чтение двух JSON при запуске и отдельные индексы `map[string]model.Company`, реализация `JSONRepository` с методами `GetEGRIP` и `GetEGRUL`.
- `internal/model`: вложенные доменные структуры и `ErrCompanyNotFound`.

Зависимости передаются через конструкторы. Handler вызывает Service; Service вызывает Repository. Handler не читает файл, Service не знает о JSON и HTTP. Ожидаемые ошибки оборачиваются с `%w` и различаются через `errors.Is`. Контекст HTTP-запроса передаётся до репозитория.

## Логирование

Приложение использует стандартный `log/slog`: один JSON-объект на строку в stdout, уровень по умолчанию — `INFO`. Каждая запись содержит время, уровень, сообщение и поле `service=registry-mock`.

Логгер создаётся в `main` и передаётся в Handler через конструктор. Запуск сервера логируется на уровне `INFO`, внутренние ошибки, ошибки записи HTTP-ответа и завершение из-за ошибки — на уровне `ERROR`. Ожидаемые ошибки некорректного ИНН и отсутствующей компании не логируются как внутренние сбои. Ошибки Service и Repository передаются вызывающему слою и логируются на границе приложения, без повторных записей в каждом слое. Внутренний журнал `net/http` направлен в тот же логгер.

## Проверки

```powershell
go fmt ./...
go vet ./...
go test ./...
go build ./...
```

Тесты создают JSON только во временных каталогах `t.TempDir()` либо используют тестовые реализации интерфейсов. Наличие пользовательских файлов в `testdata` для тестов не требуется.

Юнит-тесты находятся в файлах `*_test.go` без суффикса `_integration`: они проверяют конфигурацию, Service с подставным Repository и Handler с подставным Service.

Интеграционные тесты вынесены в отдельные файлы:

- `internal/handler/registry_integration_test.go`: цепочка Handler → Service → Repository с временным JSON.
- `internal/repository/json_repository_integration_test.go`: загрузка и поиск с использованием реальной файловой системы.
- `main_integration_test.go`: ошибка запуска при недоступном файле данных.

Все интеграционные тесты имеют префикс `TestIntegration`. Обычный `go test ./...` запускает оба набора. Для раздельного запуска:

```powershell
go test ./... -skip Integration
go test ./... -run Integration
```
