# review

Рассмотрение заявки сотрудником банка по контракту lasagna-credit-v1: очередь, назначение, запросы уточнений, решение с предложением и PDF договора. Заявка и её статусы — модуль `application`; переходы вызываются оттуда (`applicationdomain.Application`). Правку и отправку заявки клиентом (`PATCH /applications/{id}`, `submit`, `resubmit`) ведёт модуль `intake`, проверку залога (`POST /underwriter/applications/{id}/collateral-review`) — `collateral`, расчётный счёт — `company_accounts`; здесь они только читаются.

Этап начинается со статуса `manual_review`. Решение в этой версии всегда публикует сотрудник: любой исход скоринга (`completed`, `insufficient_data`, `not_configured`, `failed`) ведёт сюда. Без сотрудника заявка уходит только в `rejected` по stop-правилу конвейера.

## Права

- `/underwriter/*` — роли `underwriter` и `admin`, проверяет middleware. Черновики сотруднику не видны: 404.
- Менять рассмотрение может назначенный сотрудник (`take`) или `admin` — иначе 403 `FORBIDDEN`. Права проверяются и на заблокированной в транзакции заявке.
- Клиентские ручки — участник компании-заёмщика, участие проверяется при каждом обращении; чужая заявка — 404.

## Изменения

Каждое изменение передаёт `expected_revision`: устаревшая вкладка получает 409 `REVISION_CONFLICT` с `error.current_revision`. `reviewrepo.Repo.Update` идёт через `applicationrepo.Update`: в одной транзакции блокирует строку заявки, сверяет revision, применяет доменную функцию и пишет `reviewdomain.Change` — запрос, ответ, документ, решение, уведомление — а затем историю и заявку; revision + 1. Правка заявки в `intake` и проверка залога в `collateral` тоже увеличивают revision, так что решение не опирается на устаревший запрос или залог.

| Ручка | Что делает |
| --- | --- |
| `GET /underwriter/applications` | Очередь: `status`, `assignee=me\|none\|<uuid>`, `limit` (20, до 100), `cursor`. Старые сверху |
| `GET /underwriter/applications/{id}` | Карточка: проверки, скоринг, залог, запросы, решения, история, `decision_blockers` |
| `POST .../take` | Назначить на себя. Повтор тем же сотрудником безопасен; занятую другим — 409 `INVALID_STATE` |
| `POST .../request-info` | `message`, `editable_fields` из полей черновика → `info_requested`, уведомление клиенту |
| `POST .../decision` | `approved` / `counter_offer` / `rejected`, см. ниже |
| `POST .../retry-checks` | `sources: registry, credit_bureau`. Пока конвейер не подключён — 503 |
| `GET /applications/{id}/info-requests` | Запросы банка |
| `POST /applications/{id}/info-requests/{rid}/answer` | Ответ текстом; поля из `editable_fields` правятся PATCH заявки, повторная отправка — `resubmit` в `intake` |
| `GET /applications/{id}/offer`, `/contract` | Текущее предложение и договор; `null` — нет |
| `GET /documents/{id}/content` | PDF: клиенту — документы своей компании, сотруднику — любые |

## Решение

- `approved` — продукт, сумма, срок и обеспечение как в запросе; `counter_offer` — изменён хотя бы один из них (`changed_fields` считает сервер). Отличие ставки не делает предложение встречным. Несоответствие — 422 `outcome: OUTCOME_MISMATCH`.
- Положительное решение блокируется (422 с полями), пока не готовы проверки: ответ реестра с совпавшим ИНН и не `terminated`, отчёт БКИ (`has_credit_history=false` — это данные), принятые финансовые данные (`no_history` — только у `start`). `reorganizing` и любой статус скоринга не блокируют.
- Обеспеченное предложение (`collateral_required`) — только с проверкой залога `accepted` по текущей ревизии и хешу предмета, не старше 30 дней (`collateraldomain.CollateralReview.Current`), и сумма не больше 70% принятой стоимости (`CollateralCovers`) — те же правила, что у скоринга.
- Деньги и лимит — на активный расчётный счёт компании: по умолчанию её единственный счёт из `company_accounts`, чужой — 404 по полю.
- Овердрафт: `term_months` нет, обязательны `agreement_term_months` и `max_tranche_days` не меньше периода в днях.
- «Старт»: новая сумма сначала требует уточнить у клиента источники финансирования (`BUDGET_MISMATCH`).
- Платёж разового кредита — аннуитет по формуле ТЗ в точных дробях, до копейки, последний платёж гасит остаток.
- Отказ — из `manual_review`, с `reason_code` и пояснениями для клиента. `comment` решения и проверки залога внутренние: клиенту их DTO не содержат.
- Новые условия до подписания — новая версия предложения со своим договором; старые хранятся.

PDF договора (`reviewcontract`, шрифт Go Regular) загружается в S3 до транзакции; решение, документ и переход пишутся атомарно. Сбой хранилища — 503, заявка не меняется. Если не прошла транзакция, файл остаётся без ссылок на него.

## Граница с конвейером

Проверки собираются в два шага. Сначала `reviewrepo.ChecksRepo` читает снимки заявки от конвейера: последнюю строку `external_checks` по источнику (`completed` + ответ мока, `failed` + `not_found`, иначе недоступен) и `scoring_results` (нет строки — `not_configured`). Где снимка нет, `CheckSummary.FillFromOverview` берёт сохранённую сводку компании `company_overviews` — тот же источник, что у `scoring.Validator`; финансовых снимков версии заявки в схеме пока нет, поэтому финансы — оттуда же (CSV или автоматические). Конвейер пишет результаты с увеличением revision заявки, чтобы решение не опиралось на устаревшую карточку.

`reviewservice.Passthrough` — временная замена конвейера: после `submit` и `resubmit` (их вызывает `intake`) сразу возвращает заявку на `manual_review` без проверок, `retry-checks` недоступен. Реализация `Pipeline` из модуля scoring заменяет её в `internal/app/service.go`.

Таблицы этапа — миграция `000050_underwriting.sql`: версии и условия `credit_decisions` (счёт — ссылка на `company_accounts`) и `editable_fields` запросов уточнений.
