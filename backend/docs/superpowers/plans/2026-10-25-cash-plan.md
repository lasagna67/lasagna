# Cash plan implementation plan

**Goal:** Store the client's cash plan and Start project, record the client's confirmation and the bank's review, and fill `CashPlanConfirmed`/`CashPlanAccepted` from the database instead of trusting caller flags (stage 2 spec P09, P11, P14, C01–C04).

**Architecture:** New module `internal/cashplan` (domain, repo, dto). `intake` writes the plan and project with the application change; `underwriting` writes immutable reviews; `scoring` holds the pure calculations and the scorer reads all rows in its single snapshot query.

**Approved decisions:** `data_revision` is introduced minimally in this task (request, collateral, project and plan changes; financial snapshots are not per application yet). One current plan row, each review stores the plan hash, terms hash and data revision. The Start project calculation (P11) is included.

**Rules:**
- Whether a plan is required is computed, never supplied: Start always (`project`), overdraft never, other annuity products (`liquidity`) when the six completed months window has F < 0, G < 0.8, undefined G or an income above two medians. Fewer than three months — unknown, which routes to manual review and blocks a positive decision.
- The plan covers exactly N months starting the month after the Moscow business date. Any content change drops the confirmation; confirmation is a separate PATCH.
- Review is valid only for the current plan hash, terms hash and data revision. Accepted reserve is at most the declared one.
- Feasibility: Rs[t] ≥ 0 on the validated reserve with the real rounded schedule and D on the whole horizon; last min(6, N) months C/(D+Pmax) ≥ 1.2 and Cs/(D+Pmax) ≥ 1, compared in integers.
- Start: credit + own funds = cost items, own funds ≥ 30%, sales start inside the forecast, no income before it for a new business; result pass/needs_info/fail without a score.
- Offers relying on a plan expire within 7 days and before the next Moscow month.
